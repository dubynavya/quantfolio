# QuantFolio

A portfolio risk-analytics platform: track holdings, compute real risk metrics from live market
data, route every trade through a rule-based multi-level approval engine, forecast prices, and
run Monte Carlo Value-at-Risk simulations.

Three services, three different skill sets, wired together end to end:

| Service | Stack | What it does |
|---|---|---|
| `backend` | Java 21, Spring Boot 3, Spring Security, JPA/H2 | Auth, portfolios/holdings, the risk engine, the trade-approval engine, scheduled risk alerts |
| `ml-service` | Python, FastAPI, statsmodels, NumPy | Short-horizon price forecasting (Holt linear trend) and Monte Carlo VaR (GBM simulation) |
| `frontend` | React 19, TypeScript, Vite, Recharts | Dashboard, holdings, trade submission/approval UI, forecast charts |

No API keys required to run this — market data comes from Yahoo Finance's public chart endpoint,
so cloning the repo and running it is enough to see it work with real prices.

## Why this exists

Two smaller projects on my resume ([BookShelf Management System](https://github.com/dubynavya/mern-stack-app),
a MERN CRUD app, and [Approval Workflow System](https://github.com/dubynavya/req-approval), a
Spring Boot rule-based routing engine) each demonstrate one skill in isolation. QuantFolio combines
them deliberately:

- The **approval engine** in `backend/.../approval/ApprovalEngine.java` is a direct successor to
  `req-approval` — same idea (multi-level, rule-based routing) — but the rules now evaluate live
  notional value and *computed* portfolio concentration instead of static fields, and the outcome
  actually gates whether a trade touches your holdings.
- The **risk engine** (`backend/.../risk/RiskMath.java`) is real, hand-derived financial math —
  annualized volatility, Sharpe ratio, max drawdown, historical VaR, beta — not a wrapper around a
  library, and it's unit tested (`RiskMathTest.java`, `ApprovalEngineTest.java`).
- The **ML service** is a separate Python microservice the Java backend calls over HTTP, which is
  a realistic shape for how forecasting/ML actually gets bolted onto a JVM system in practice.

## How the approval engine works

Every trade submitted via `POST /api/portfolios/{id}/trades` is evaluated against two live
numbers: its notional value, and the portfolio concentration it would *result in* if executed.

| Level | Condition | Outcome |
|---|---|---|
| 1 | Notional ≤ $10k **and** resulting concentration ≤ 20% | Auto-approved, holdings updated immediately |
| 2 | Notional ≤ $50k **and** resulting concentration ≤ 40% | Held `PENDING_CONFIRMATION` — needs explicit sign-off |
| 3 | Anything larger/riskier | Held `PENDING_CONFIRMATION` with a high-risk reason list |

The reasons shown in the UI are generated by the same evaluation call — nothing is hardcoded per
level, so the message always matches the actual thresholds in `application.yml`.

## Risk metrics

Computed in `RiskEngineService`, from the intersection of trading days across every holding and
the S&P 500 benchmark:

- **Annualized return / volatility** — from daily portfolio-value returns, 252-day convention
- **Sharpe ratio** — vs. a configurable risk-free rate
- **Max drawdown** — largest peak-to-trough decline in the equity curve
- **Historical VaR (95%)** — empirical loss at the 5th percentile of the return distribution
- **Beta** — covariance with SPY / variance of SPY

A scheduled job (`RiskAlertScanJob`, every 6h by default) re-runs this for every portfolio and
raises alerts on threshold breaches; there's also an on-demand `POST /alerts/scan` for demos.

## Forecasting & Monte Carlo (ml-service)

- `/forecast/{ticker}` fits **Holt's linear trend** (double exponential smoothing) rather than
  something heavier like ARIMA or an LSTM — daily equity closes are close to a random walk, so a
  simple, well-understood trend model is an honest reflection of how much signal is actually
  there, with a 95% interval that widens with `sqrt(horizon)`.
- `/risk/monte-carlo/{ticker}` estimates drift/volatility from historical log returns, simulates
  thousands of Geometric Brownian Motion price paths, and reports VaR/CVaR from the simulated
  distribution — a complement to the backend's *historical* VaR, since Monte Carlo also covers
  plausible-but-unobserved scenarios.

## Running it

### Option A — Docker Compose (easiest)

```bash
docker compose up --build
```

Frontend: http://localhost:5173 · Backend: http://localhost:8080 · ML service: http://localhost:8000

### Option B — run each service locally

**Backend** (Java 21, Maven):
```bash
cd backend
mvn spring-boot:run
```
Runs on `:8080` with a local H2 database file (`backend/data/`) — no setup needed. Switch to
Postgres in production with `SPRING_PROFILES_ACTIVE=prod` and the `DATABASE_URL` env var.

**ML service** (Python 3.12+):
```bash
cd ml-service
python -m venv .venv && .venv/Scripts/activate   # or source .venv/bin/activate on macOS/Linux
pip install -r requirements.txt
uvicorn main:app --port 8000
```

**Frontend** (Node 20+):
```bash
cd frontend
cp .env.example .env
npm install
npm run dev
```
Open http://localhost:5173, register an account, create a portfolio, add a holding (try `AAPL`,
`MSFT`, `SPY`), and the dashboard will pull real price history to compute risk metrics.

## Tests

```bash
cd backend
mvn test
```

`RiskMathTest` and `ApprovalEngineTest` cover the pure financial/routing logic (drawdown, Sharpe,
VaR, beta, and every approval-level boundary) independent of Spring or the database.

## Limitations & honest trade-offs

- **Yahoo Finance's endpoint is undocumented and unofficial.** It's used because it needs no API
  key, which matters for a project meant to be cloned and run by anyone — but it could change or
  rate-limit without notice. A production system would use a paid, contracted data vendor.
- **Historical VaR and the Holt forecast both assume the recent past is a reasonable guide to the
  near future.** Neither accounts for regime changes, earnings events, or macro shocks.
- **The approval engine's thresholds are illustrative**, not derived from any real risk policy —
  they're configurable in `application.yml` for a reason.
- **Single risk-free rate and a single benchmark (SPY)** — no per-asset-class benchmarking.
